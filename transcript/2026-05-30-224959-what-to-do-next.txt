❯ is it easy if i want to redesign the ui later onward after we execute the     
  plan?                                                                         

● Yes, very easy. The codebase is structured to keep UI completely separate from
  logic:

  - src/game/ — pure math, no UI
  - src/stores/ — state, no UI
  - src/db/ — data, no UI
  - src/screens/ and src/components/ — UI only, reads from stores

  Redesigning later means touching only src/screens/, src/components/, and
  src/theme/. The data layer, game logic, and state management stay untouched.

  The theme system (colors.ts, spacing.ts, typography.ts) is also centralized —
  a color palette or font swap is a one-file change that ripples everywhere
  automatically.

  The one caveat: if Phase 2 builds UI that's tightly coupled (e.g. business
  logic embedded directly in screen components instead of in stores/hooks), that
  makes redesign harder. The plan avoids this by convention — but it's worth
  keeping an eye on during Phase 2 execution to make sure logic stays in
  hooks/stores, not screens.

  Short answer: yes, a redesign later is low-risk and well-scoped given the
  architecture.

❯ how do i rerun, can i type npm run start -c ?                                 

● npm run start -c won't work — npm interprets the -c itself rather than passing
  it to the script.

  Use this instead:

  npm run start -- -c

  The -- tells npm to forward everything after it to the underlying script. That
  expands to:

  REACT_NATIVE_PACKAGER_HOSTNAME=100.69.13.58 expo start --dev-client -c

  Or just run the full command directly if you prefer to be explicit:

  REACT_NATIVE_PACKAGER_HOSTNAME=100.69.13.58 npx expo start -c --dev-client

  Both do the same thing — start Metro with the cache cleared.

● This is largely not a code problem — it's the nature of ARCore on Android. Let
  me break it down:

  Why it's slow to detect (30 seconds):
  ARCore works by identifying visual "feature points" — tiny texture details on
  surfaces. It needs to see the same surface from multiple angles to understand
  its depth and flatness. Plain surfaces (white floor, glass table, solid-color
  carpet) have almost no features, so ARCore struggles. Textured surfaces (wood
  grain, tiles, patterned carpet) detect in 2-3 seconds. You also need to move
  the phone slowly in a sweeping motion — holding still actually makes it worse
  because ARCore needs parallax to compute depth.

  Why it flickers:
  ARCore continuously refines its plane estimates as it gets more data. A plane
  that was "detected" at 70% confidence gets updated, sometimes reclassified,
  sometimes split into two planes. The ViroARPlaneSelector shows/hides the
  overlay each time ARCore fires an anchor update event — that's the flicker
  you're seeing. This is normal ARCore behavior on devices without a depth
  sensor.

  The real answer — hardware:
  Your proposal already states the primary target is iPhone 15 Pro (LiDAR).
  LiDAR is a dedicated hardware depth sensor that doesn't rely on visual
  features at all — it fires infrared lasers and measures time-of-flight. Plane
  detection on iPhone 15 Pro is near-instant (under 1 second), rock-solid, and
  works on plain white floors. Android without LiDAR relies entirely on
  camera-based feature matching, which is inherently slower and less stable.

  - Demo the AR on iPhone, not Android

● Good specific question. There are a couple of real code-level improvements for
  this:

  1. useActualShape={false} — most direct fix

  By default useActualShape={true} makes Viro use ARCore's actual polygon
  boundary to draw the plane overlay. That polygon closely traces whatever
  ARCore thinks the plane edge is — including shadow lines. So a shadow on the
  floor makes the overlay morph and flicker along the shadow edge because ARCore
  keeps redrawing the polygon boundary there.

  Setting useActualShape={false} uses a simple bounding rectangle instead. The
  rectangle is much less sensitive to shadow-induced boundary changes — it just
  shows a stable box over the detected region. Less accurate to the true plane
  shape, but far more stable visually.

  2. Stability filter via onPlaneDetected

  We can reject planes that haven't stabilised yet by only accepting them after
  they've been around for a few consecutive updates. Shadow-split spurious
  planes tend to appear and disappear quickly — a real floor plane persists. We
  could track how many times a plane has been updated and only show it after N
  confirmations.

  3. Switch to hit-test placement instead of plane overlay

  This is the most elegant solution. Instead of showing a plane overlay the user
  has to tap, we use onARHitTestResults on ViroARScene — the user just taps the
  screen anywhere, and ARCore tests what surface is at that screen position
  using multiple methods (existing planes, feature points, depth). It bypasses
  the plane visualisation entirely, so shadow-split planes never become a visual
  problem. The pet just appears wherever you tap.

  This is actually how most polished AR apps work — Google's ARCore demos, IKEA
  Place, etc. all use hit testing rather than explicit plane selection overlays.
  It's more intuitive too.

  Ranking for your situation:
  1. Hit-test placement → eliminates the problem entirely, also better UX
  2. useActualShape={false} → quick, meaningful stability improvement
  3. Stability filter → reduces noise but adds complexity

  Want me to implement all three?
