● What the error actually means

  AR_ERROR_SESSION_PAUSED → "Cannot update frame, session is paused" spamming on
  every frame means exactly one thing:

  ▎ Your GL render loop is running and calling session.update() to pull camera 
  ▎ frames, but the ARCore session is not in the resumed state. 
  ▎ ArSession_resume() either was never called successfully, or 
  ▎ ArSession_pause() was called and never reversed.

  The black screen is the symptom of that: no camera frame is ever delivered to
  the GL surface, so it stays black while the renderer keeps ticking and logging
  the error each frame.

  Camera permission being granted is a red herring. Permission gates whether the
  session can open the camera; this error is one layer past that — the session
  is open but parked in the paused state. So stop chasing permissions.

  Why it broke with zero code changes

  If the JS/native code is byte-identical to the commit that worked 2 days ago,
  the variable that changed is on the device, in the native AR lifecycle, not in
  your bundle. In order of likelihood:

  1. Google Play Services for AR (ARCore) auto-updated on the phone. This is the
  #1 cause of "worked Tuesday, black screen Thursday, no code change." The
  ARCore APK updates silently in the background and periodically desyncs with
  Viro's native session handling until the app is rebuilt/reinstalled. Check:
  adb shell dumpsys package com.google.ar.core | grep versionName and note if it
  bumped.
  2. The AR Activity is mounted but never actually onResumed — something is
  sitting on top of it so Android considers it not-foreground, so Viro never
  fires resume. Suspects in your app: a modal/overlay rendered over the AR
  screen (daily check-in modal, offline banner), an incomplete React Navigation
  transition (AR scene mounts while still behind another screen), or the
  Metro/dev-menu overlay. The session opens, the activity pauses immediately,
  render loop keeps going → exactly this spam.
  3. Stale dev build / native↔JS mismatch. If you pushed a JS-only update (OTA
  or fast refresh) but the installed native binary is older, the Viro native
  lifecycle and the JS scene can disagree. Reinstall the dev client fresh.

  Triage order

  1. Reinstall/rebuild the app fresh (adb uninstall then reinstall the dev
  build) — this clears both the stale-binary case and re-pairs with the updated
  ARCore. Fastest highest-value check.
  2. Confirm whether ARCore updated (dumpsys version above). If it did and a
  fresh install fixes it, that was your cause.
  3. Watch the activity lifecycle while entering the AR screen: adb logcat | 
  grep -iE "onResume|onPause|ViroActivity|resume". If you see the AR activity go
  onResume → onPause instantly, something is overlaying it — that's cause #2,
  and the fix is making sure the AR scene only mounts when its screen is
  actually focused/foreground (gate mount on navigation isFocused, and don't
  render the check-in modal / overlays over it).

  My bet, given "no code change in 2 days," is #1 (ARCore auto-update) — fixed 
  by a clean reinstall. Start there.

  Want me to look at how ARWalkScreen mounts the Viro navigator relative to
  navigation focus and the modal/banner overlays, to rule out cause #2 in the
  code?

  ARCore is a visual-inertial tracker: no IMU → no motion tracking → it can't

  Why the IMU source fails with unchanged code

  Two non-code causes, in order of likelihood for a "worked 2 days ago"
  situation:

  1. The device's sensor service/HAL has wedged. ARCore's android_sensors.cc

  symptom — the Android sensor service gets into a bad state and silently
  refuses new registrations until restarted. Same binary works again after a

  aren't in the foreground. If anything is over the AR view — a lingering

  see a clean tracking state after.

❯ is there any quick tool for me to check if all sensors on my device is ok? or 
  the physical sensor is not the issue?                                         

● Yes — several quick ways, from "no install" to "definitive." Start with adb
  since you already have it wired up.

  1. adb — zero install, tells you if sensors even exist

  List every sensor the device exposes:

  adb shell dumpsys sensorservice | grep -iE "gyro|accel|magnet|rotation"

  What you want to see: at least an accelerometer and a gyroscope line. ARCore
  requires a gyroscope — if there's no gyro line at all, the device isn't
  ARCore-capable and that's your whole answer (but it worked 2 days ago, so it
  almost certainly has one).

  2. adb — see if sensors are actively streaming (the real test)

  This is the one that distinguishes "hardware dead" from "wedged service /
  background block":

  adb shell dumpsys sensorservice

  Look at the top section:
  - Active sensors: — lists sensors currently registered with active clients.
  Open a sensor app (below) and you should see gyro/accel appear here.
  - Sensor Device: and recent event timestamps — if numbers are updating between
  two runs, the HAL is alive.
  - If Active sensors stays empty even with a sensor app open, or you see
  errors, the sensor service is wedged → reboot.

  Quick "are values changing" check — run this twice while moving the phone:

  adb shell dumpsys sensorservice | grep -A2 -iE "gyro|accel"

  ▎ Failed to register sensor to queue 0. Apps like AR Toolbox are immune 
  ▎ because their sensor stack keeps those sensors continuously active.

● Yes — that's exactly the right convention, and it'll make your AR placement
  "just work" with zero code offsets. Let me explain why in terms of how your
  app actually places the pet, plus the catches.

  Why it's correct

  In PetARScene, the pet renders as a Viro3DObject at position={[0,0,0]} inside
  a ViroNode that's positioned at the surface hit point (on the ground plane).
  So the model's origin lands exactly on the ground where the user tapped.

  - Origin at the feet / ground-contact point (Y=0 at the base), centered in X/Z
  → the pet stands on the surface, right where they tapped.
  - Origin at the geometric body center (common Meshy default) → half the model
  sinks below the floor, and you'd have to fudge a vertical offset in code
  per-model. Avoid that.

  So: bottom-center pivot is the move. X/Z centered so it appears at the tap
  point; Y at the contact plane.

  The critical part: consistency across poses AND animation frames

  This pairs with your scale normalization — both scale and origin must be
  identical conventions across every pose, because:

  1. Pose switching — the app swaps models live (e.g. normal → walking when the
  pet follows). If pet_dog_stand and pet_dog_run_1 have different origins, the
  pet will jump vertically/sideways the instant it changes pose.
  2. Frame-cycled animations — walk/excited/happy are multiple GLBs cycled by
  toggling visible. So run_1, run_2, run_3 must share the exact same origin, or
  the pet will jitter/hop every frame. This is the one most likely to bite —
  align those frame sets carefully against each other.

  A practical way: pick one reference pose (e.g. stand), set its bottom-center
  origin, then align every other pose/frame so the feet sit at that same origin.

  One nuance: airborne poses

  For poses with no ground contact — pet_bird_fly_1/2, pet_bird_jump_1/2,
  pet_cat_jump — "center of the standing ground" still means: put the origin at
  the ground point directly beneath the creature (X/Z centered, Y=0 at floor
  level), and let the body float above it at whatever natural hover height you
  want. That way a flying bird hovers at a consistent height above the tap point
  instead of being half-buried — and it won't pop when transitioning to/from a
  grounded pose.

  Bonus: it also fixes rotation and the idle pulse

  - Your follow logic rotates the pet around Y (petYRot) to face the user — with
  a centered base pivot it spins in place instead of orbiting.
  - The petIdlePulse scale animation pulses around the origin — feet-pivot makes
  it look like it's planted and breathing rather than scaling from its belly.

  So: bottom-center, ground-contact origin, consistent across all poses and all 
  animation frames (and ground-projected for airborne ones). Do that plus the
  uniform scale, and the code just renders at [0,0,0] with an age multiplier —
  no per-model hacks.
